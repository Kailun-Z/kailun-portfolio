研发指标体系与数据平台

给华为英国研发中心的研究所所长、COO、项目经理和三个研发组主管，把"项目能不能按里程碑交付、要不要调人和预算"从双周例会后的人工 Excel，变成一个有独立网址、按三类角色分层、每个数字能点回原始任务的数据平台。

简历对应条目
华为技术研发（英国）· 数据分析工程师 · 研发指标平台负责人
给谁做
华为英国研发中心：研究所所长 / COO、项目经理、3 个研发项目组主管与成员
我的角色
唯一数据负责人：口径定义、相关方对齐、管道与后端开发、上线推广；后期带 3 人小组
展示方式
公司内部系统，不公开截图；本页为描述型案例，架构与口径为抽象表述

问题

主管判断不了项目能否按期交付，数据每两周靠人工算一次，常出错、查不到来源

  1. 一
    决策滞后。所长和 COO 要在双周例会后才拿到人工整理的数字，发现延期或人力缺口时已经晚了。
  2. 二
    人工统计贵且不可信。每组每次从两个平台下载数据、导进三张模板 Excel 计算、再回填项目管理网站，耗时数小时，经常出错，也查不到某个数来自哪条记录。
  3. 三
    口径不统一。三个组对迭代周期和任务的用法各不相同，"完成率""延期"没有一套所有人认可的定义，数字之间无法比较，也没人愿意为"没干完"被看见。
方案

口径先行、评审通过再开发；用变更记录重建历史，而不是信任当前状态

1 · 驻进研发团队定口径

梳理项目 / 迭代周期 / 任务三层的业务逻辑，把"完成率、跨期延期、基于历史效率的交付预测"定义成可计算的公式，拉通项目主管、team leader 和成员逐一评审，全部通过后才开发。上线一次过，没有返工。

2 · 技术核心：从"当前状态"重建"历史"

项目管理系统只记任务现在在哪个迭代；任务被挪走后，上一个迭代的指标就被污染了。平台不用当前字段，而是拉取任务的变更记录，重建每个任务的历史归属链（如 Sprint N → Backlog → Sprint N+1），再把承诺 / 新增 / 跨期流转这些口径固化进可重复运行、可回归验证的管道。

3 · 按三类角色分层展示

所长 / COO 看项目完成度与人力预算缺口；主管看团队效率与延期风险；成员看个人迭代产出。汇总数字可下钻到该迭代的任务明细和导出表。

架构

一次完整运行怎么走

口径

最花功夫的一层：把"完成率""延期"定义成所有人都认的公式

指标公式（分子 / 分母）规则要点给谁看
承诺工作量承诺窗口内归属该迭代的任务工作量点数之和由变更记录判定归属，不用当前字段高层、主管
中途新增工作量新增窗口内加入的任务工作量点数之和把"范围变了"和"没干完"分开主管、成员
承诺完成率已完成工作量 ÷ 承诺工作量主管最在意的那个数；目标值约四分之三高层、主管
最终完成率已完成工作量 ÷（承诺 + 中途新增）两个分母并列报告，指标公平了大家才接受高层、主管
跨期流转次数任务历史归属链中跨迭代事件数跨期不等于延期；流转超过 2 次才预警，是否计划内留给主管判断主管、成员
每人每迭代产出已完成工作量 ÷ 等效人力人力数据缺失时返回空值 + 警告，不硬填分母高层、主管
里程碑完成率已完成用户故事点数 ÷ 里程碑总点数与交付预测配合看风险高层、主管
交付预测剩余工作量 ÷ 近 3 个迭代滚动人效 = 还需几个迭代定义在指标层，对比里程碑日期给风险等级；未做成自动字段高层、主管
数据质量与可复现

三道防线，关键指标准确率 100%

  1. 1
    不信当前状态，用变更记录重建历史。成员误改数据时能定位到时间点和改动前后值；历史迭代的指标不随后来的修改漂移。
  2. 2
    按日期快照，可对比可回滚。每次运行把任务、迭代、指标集合按运行日期保存，最新结果与历史结果并存。
  3. 3
    黄金样本回归。固定一个项目 + 一个迭代作为基线，改代码前后关键指标与导出产物必须一致；"准确率 100%"指的是这个回归，不是逐条人工核对。

管道按阶段输出标准产物（任务明细、指标汇总、迭代目录、里程碑结果、可下载报告）。曾因上游未产出某个中间文件导致报告阶段失败，之后定了统一的产物清单作为上下游契约。

结果

从双周事后复盘，到实时监测与事前预测

项目之前之后
高层拿到数据双周例会后，人工整理打开网页即看完成度与缺口；成为实时汇报与绩效评审依据
主管的决策时点例会后算两小时才知道哪里有问题例会前就知道要讨论哪个项目、要不要调人
例行统计三组每两周各数小时人工自动化，效率提升约 120 倍
数字可信度常出错、查不到来源每个数能点回原始任务记录；主管和成员不再为"这个数对不对"争
管道耗时5 分 30 秒1 分 06 秒（−80%）

在这之前我先做了研究院层面 300+ 项目的管理看板：拉通项目经理、研发、HR、财经四方口径，定义进度 / 人力 / 财务偏差指标与橙红两级预警，上线即识别出 10+ 起项目已截止但人力预算仍在发生的异常，推广到德国研发中心。两者是两层：看板管项目组合，本平台管研发团队的执行。

我的角色

唯一数据负责人

从口径定义、相关方对齐到后端开发上线全程自己做；后期作为项目负责人带 3 人小组，我负责指标层、后端数据开发与前端设计，并向前端提供接口。技术栈：Python 管道 + MongoDB + FastAPI，后期 Docker 化。

局限与下一步

自己先说的

  • 交付预测停在指标层，没做成自动预测字段；下一步按历史人效波动给区间估计。
  • 调度靠按需运行，不是严格实时；做法是按 updatedAt 增量拉取 + webhook 触发。
  • 可溯源下钻到迭代明细，没接到任务 URL；明细每行有任务 id，是前端加一个下钻组件的事。
  • 黄金样本只有一个；要做成持续验证，加对账步骤并扩到每个项目各一个。

公司内部系统，不展示界面与数据。本页架构与口径为抽象表述，数字取量级。面试时可就口径设计、历史重建与验证机制展开。
